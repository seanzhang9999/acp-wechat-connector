# 阿维上下文自动轮换（v0.16.0）

腾讯 iLink 和 WorkBuddy 都使用同一个 ACP 语言服务。管理会话达到阈值后，阿维在下一条完整用户请求开始前关闭旧管理连接，需要理解自然语言时再创建新会话。无需定时调用模型，无需关闭微信或 Codex 桌面。

## 默认策略

- 收到 `usage_update` 后记录最新有效 `used/size`，达到 75% 时准备轮换。使用最新窗口占用，不累加计费 token；上游压缩导致用量下降时随最新值更新。
- 每个会话 80 次模型调用或累计 240000 字符也是独立上限，即使用量通知缺失仍能轮换。字符包括发出的完整提示和返回文字，是保守的工作量限制，不是准确 token 估算。
- 同一次用户请求可能有多次模型调用。无论是否达到阈值，都先让这条请求按原有步骤/超时限制结束，下一条请求才轮换。不是绝对防溢出保证：单次巨大输入或查阅仍可能触及窗口，失败会报告，不自动重放。
- 仅关闭阿维独立管理 ACP 子进程；不重启整个 iLink 桥、不切换或重建业务 Codex 会话、不操作桌面应用。
- 新管理会话继续经过内部会话登记与列表过滤。旧会话历史保留，不自动删除；不意味着磁盘历史数量不再增长。

## 状态延续

控制器与路由对象继续保留：业务目标、未过期候选、历史查阅游标、待确认操作及其原有过期时间。模型轮换不会重新授权、执行或延长确认。原有规则仍有效，例如普通新请求会取消此前待确认动作。

最近三条管理请求及各自末尾两段已发送回复，以有长度限制的记录注入下一次理解。每段最多约 900 字符，截断有标记；不同用户分开保存。记录只用于指代，不能替代本次指令、确认或查阅证据。长回答后继续追问，仍需重新读取必要来源。

这些近期记录仅在当前桥进程内存中保留。自动轮换模型会话会保留它们，整个桥进程重启不保证恢复全部临时状态。WorkBuddy 本身的聊天上下文及业务会话的上下文管理不属于此功能。

## 微信侧使用

正常发消息即可，无需开启开关。查看状态：

> 阿维，上下文状态

这是一条程序直接回答的管理指令，不消耗模型调用，也不主动轮换。显示最近上报用量（未收到时明确提示）、阈值、当前累计调用/字符、本进程轮换次数。正常自动轮换不额外发送装饰图或提醒刷屏，stderr 有 `[awei-context] rotated reason=... count=...`，不记录对话正文。

## 调整阈值

使用代码配置的 iLink 启动器：

```javascript
config.awei = {
  ...config.awei,
  rotation: { usageRatio: 0.75, maxCalls: 80, maxCharacters: 240000 }
};
```

WorkBuddy 的连接器 config.json：

```json
{
  "aweiRotation": {
    "usageRatio": 0.75,
    "maxCalls": 80,
    "maxCharacters": 240000
  }
}
```

这只是增加到现有配置的字段，保留其他字段。usageRatio 必须大于 0 且小于 1，另外两项必须是正整数。省略即启用上述默认值。修改配置前备份，重启对应桥进程后生效。

## 验收步骤

1. 更新并重新启动对应桥，在微信发送“阿维，上下文状态”，应报告自动轮换已启用。
2. 普通使用：搜索会话、切到候选、查看最近对话、再往前看，确认目标和游标正确。
3. 如需快速验收，在独立测试实例临时设置 maxCalls=2（不要用生产实例强行填满上下文）。一条复杂查询即使调用多次模型也应完整结束；下一条自然语言请求前轮换。
4. 再问上下文状态，应看到轮换次数增加；“切到第二个”和“继续往前看”仍按有效候选及查阅状态工作。
5. 涉及释放/退出的确认仍须用户新消息，超时确认不能因轮换复活；不要在真实桌面上仅为测试执行关闭。
6. 恢复默认阈值。后台应只出现轮换原因/次数，私人正文不会写入轮换日志。

自动测试使用本地 ACP 协议模拟进程，覆盖真实连接重建、usage/calls/characters 三种触发、同一请求不重建、上游用量下降、异会话用量隔离、超时不重放、路由和确认保留。模拟测试不代表已完成手机端高上下文端到端验收。
